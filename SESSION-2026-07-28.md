# Portal session, 28 July 2026

Started from a read of every Sage conversation in the database, looking for
software problems couples had reported and nobody had actioned. Ended up
fixing those plus the Zoom and highlights pipeline behind them.

Source material: 573 Sage messages (258 from couples) across 45 weddings, 35
uncertain questions, and the Zoom, planning-notes, shuttle and storage tables.
Every root cause below was reproduced against the live database, not inferred
from reading code.

---

## What couples reported, and what was actually wrong

### Shuttle Schedule tab "does not work" — Korey Zarate, 28 July

Confirmed. "Generate Suggested Runs" sent `seat_count: ""` and
`shuttle_schedule.seat_count` is an integer column, so Postgres rejected every
insert with `22P02 invalid input syntax for type integer: ""`. Adding a run
manually with the seats box left blank failed identically. Korey asked Sage for
a shuttle schedule at 00:42 and reported the tab dead at 00:45.

Fixed as a class rather than a line. `server/middleware/coerce.js` turns `""`
into `null` for every numeric, boolean, date and time column in the schema,
mounted globally after `express.json()`. The 115-column list was generated from
the PostgREST schema spec, not written by hand; regenerate it with
`node scripts/generate-coerce-list.mjs` after any migration that adds such
columns. Names that are numeric in one table and text in another are excluded,
because for those `""` can be legitimate (`high_chairs_count` is the only one
today).

Also in `ShuttleSchedule.jsx`: generated runs now carry an explicit `sort_order`
so a batch keeps its sequence, the loader uses `apiFetch` instead of bare
`fetch`, and a failed generate reports the actual server error rather than just
a count.

### "Chat with Sage" never crosses off — Grace Teeters, 2 March

Confirmed, and it affected everyone, not just her. The onboarding progress
endpoint queried `messages` filtered by `wedding_id`, but that table has no such
column — Sage chat keys off `user_id`. The query errored, returned null, and
`first_message_sent` was permanently false. Now resolves the wedding's profile
IDs first and filters on those. Verified against Grace's wedding: the flag now
evaluates true.

### Photo upload fails and says nothing — Grace Teeters, 2 March

Confirmed. The `couple-photos` bucket caps at 5MB, as do `inspo-gallery` and
`borrow-catalog`, while multer accepts 50MB. The server took the file and
Storage rejected it at the end. There was no client-side size check anywhere.
Grace worked out the 5MB limit herself after several tries.

`src/utils/image.js` now downscales oversized images in the browser before
upload, stepping quality down until they fit. Applied in CouplePhoto,
InspoGallery, PhotoBucket and the Dashboard uploader. HEIC files are left alone
since most browsers can't draw them to a canvas.

### Wedding date shows a day early — Ashley Hermsmeyer, 1 March

"it says my wedding date is Friday Oct 2 but it is Saturday Oct 3." Confirmed:
`wedding_date` is a DATE column, and `new Date("2026-10-03")` parses as midnight
UTC, which is 2 October in Eastern time. The Dashboard and wedding website
already guarded against it. The print view did not, and nor did AdminInbox,
AdminWeddingList or AdminWeddingProfile — the print view being the day-of
paperwork.

`src/utils/dates.js` holds `parseDateOnly`, `formatDateOnly` and
`daysUntilDateOnly`, and all five call sites now use them. The file documents
which columns are DATE and which are timestamptz, since the fix is wrong for
timestamps.

### "It is not letting me add another vendor" — Ashley Hermsmeyer, 24 April

The vendor type dropdown was restricted to the venue's configured list and the
field was `required`, so a couple with a vendor type that wasn't on it had no
way through the form. Added a "Something else…" option with a free-text field.
Editing a vendor stored under a custom type now reopens in custom mode rather
than showing a blank type.

## Zoom: transcripts were being pulled, then thrown away

The sync does download the full WEBVTT transcript. Two things broke after that.

**Extraction read the first 2,000 characters.** The sync called
`extractPlanningNotesAI(transcriptText, weddingId, source)` and omitted the
fourth argument, so `sourceType` defaulted to `'message'`. That skipped the VTT
cleanup, dropped the limit from 30,000 characters to 2,000, cut output to 800
tokens and used the shallow prompt. Two thousand characters of raw VTT is
timestamps and "Hello? / Hey, how you doing?". Every planning meeting was being
mined from its first thirty seconds. This was the main reason the highlights
read as thin.

Fixed, and gone further: transcripts are now split into 24,000-character
overlapping windows and every window is read, on Sonnet rather than Haiku, with
near-duplicate notes merged afterwards. Short chat messages stay on Haiku.

**Dedup had been dead since 6 March.** `processed_zoom_meetings.participant_names`
is a `text[]` column, but the code joined the names into a string, with a comment
claiming it was TEXT. Every insert failed with `malformed array literal` and the
error was only logged, so the loop carried on writing notes. 19 meetings had
produced 47 transcript notes, some six deep.

The insert now passes the array, and a meeting that cannot be marked as
processed is skipped rather than imported, since importing it again is worse
than missing it. `savePlanningNotes` also refuses exact duplicates as a second
line of defence, and the transcript note itself checks for a prior copy.

## Why the highlights were thin

Beyond the Zoom problem, `/api/notes-highlights` dumped every planning note in
raw and gave the model contract *filenames* as its only structured fact. No
wedding date, no guest count, no allergies, no vendor status, no timeline, no
staffing. Output was capped at 1,000 tokens against a generic four-bucket
prompt.

And the notes themselves were mostly noise. Rixey's own SMS autoresponder,
"Thanks for texting! We will text you back ASAP!", had been filed as a planning
note **296 times**. The existing auto-reply filter was a regex list that didn't
match it.

Three changes:

1. **`buildWeddingContext()`** extracted from the admin Q&A endpoint and shared
   by both. Highlights now sees everything the Q&A does: the wedding row, days
   until the date, planned guest count from the staffing answers, RSVP counts,
   contracts, allergies, vendors, timeline, decor, bedrooms, staffing, checklist
   and internal notes. Notes are stripped of email markup, filtered for venue
   boilerplate, deduped and capped, newest first.

2. **Template detection that maintains itself.** Any outbound SMS body sent
   verbatim to two or more couples and appearing five or more times is a
   template. Threshold set at both, because "Sounds good!" is a real reply that
   two couples happened to receive. Patterns alone will always miss the next
   template.

3. **A coordinator's briefing rather than a summary.** Five sections: where this
   stands, needs a decision or a nudge, watch out for, the human bit, facts
   worth having to hand. It is told to compare sections against each other and
   to say when something is unknown rather than fill the gap.

Tested against Cat & Josh. It found a date discrepancy between the contracted
date and several timeline notes, a linen conflict (the table layout says white,
Rixey's included linen is ivory), a name mismatch between an allergy-registry
entry and a bridesmaid mentioned on the Zoom call, and flagged that the DJ they
want is a single-operator who can only do one event a day.

## Alert Client

Sage tells couples "I've flagged it for the human team to double-check, they'll
follow up if there's anything to add." Nothing ever did. Isadora could answer
the question and file it in the knowledge base, but the couple who asked was
never told. 31 questions are sitting unanswered, the oldest 95 days old.

Delivery goes to the couple's **Inbox** as a message from the Rixey team, Isadora's
choice, so the correction reads as coming from a person rather than from Sage.

- `POST /api/uncertain-questions/:id/alert-client` writes the direct message,
  raises a client notification and the usual new-message email, and records the
  send against the question. The bookkeeping update is deliberately non-fatal:
  the couple has already been messaged by that point, so a failure there must
  not report the send as failed.
- `POST /api/uncertain-questions/:id/draft-client-message` rewrites the
  knowledge-base answer as something you would actually send a person. The KB
  entry is written for Sage to read; this is written for the couple, and it
  opens by referring back to what they asked.
- In the admin queue, saving an answer now moves straight to the send step
  pre-filled rather than dropping the question off the list. An already-answered
  question shows "Alert client →", and one that has been sent shows the date.

**Migration `009_uncertain_question_client_alerts.sql` has not been applied.**
The service-role key is data-plane only, so it cannot run DDL. Run it in the
Supabase SQL editor. Until then the feature works and the message sends, but the
send is not recorded against the question, and you will get a toast saying so.

## Email to info@rixeymanor.com

Everything used to email the moment it happened, so the inbox filled with "a
couple uploaded a photo" and the things that needed a person were buried in it.

- **Urgent, sent immediately**: `escalation` (a couple sounds distressed or has
  asked for a human) and `new_message` (a couple has written to the team and is
  waiting). Subject `[PORTAL URGENT] …`.
- **Everything else** waits for the daily memo. Subject `[PORTAL] Daily memo —
  {date} · N waiting on you`.
- The memo now opens with **Waiting on you**: every unanswered Sage question,
  named by couple, with how long they have been waiting. A quiet day still gets
  a memo if anything is outstanding, because that is exactly the day it would
  otherwise be forgotten.
- Couples' emails no longer get the `FROM PORTAL —` prefix, which they were
  previously receiving.
- `POST /api/admin/daily-memo` returns the memo without sending it. Pass
  `{ send: true }` to actually send.

## Data cleanup

`scripts/dedupe-planning-notes.mjs`, dry run by default, `--apply` to delete.

Removed 1,145 planning notes: exact duplicates from the broken Zoom dedup, and
Rixey's own SMS autoresponder boilerplate. Kept the oldest copy of every group.
7,362 notes remain, zero duplicates, zero autoresponder notes. Zoom transcript
notes went from 47 to 20.

The script paginates by `created_at` **and** `id`. Sorting by timestamp alone
was unstable across pages when a batch import gave many rows the same timestamp,
so duplicates landed in a different page each run and the pass never converged.

## Also fixed along the way

- **The server could not start locally.** `middleware/auth.js` builds its
  Supabase clients at module level and was imported at line 9, but
  `dotenv.config()` ran at line 18. ES module imports are all evaluated before
  the first statement of the importing file, so auth.js always ran against an
  empty environment. On Railway the variables are already in the process
  environment and nothing showed. `server/env.js` now loads the environment and
  is imported first.
- **"Needs Attention" was a bare count.** It now names every couple and links
  straight to their profile, landing on the conversation that triggered the
  flag. "Sage Needs Help" is clickable too.
